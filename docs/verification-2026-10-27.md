# Проверка Invella — 27.10.2026

## Подтверждённый styles/timeout на ноутбуке

Следующий снимок показал одновременно зелёное «Вход выполнен» и `styles/timeout`. Авторизация дошла до положительного ответа, но приложение не загрузилось. В журнале появился отчёт региона arn1 `1ffbd37d63`: начало повторного запуска, начальное оформление есть, SDK/приложение/медиа ещё отсутствуют. Механизм сетевого сбоя по этому отчёту не установлен.

Добавлена функция `invella-assets` (Supabase, версия 1): она отдаёт только разрешённые части публичного кода, проверяет publishable-ключ, Origin, параметры и ответ фиксированного upstream. Не использует service role, базу, cookies или JWT посетителя. Ответы сверяются по версии и SHA-256 клиентом. Начало новой доставки проверено живым HTTP-запросом: styles 200, правильный CORS; неверный ключ 401, запрос invitations 400. Это проверка доступности нового маршрута из среды проверки, не с ноутбука пользователя.

Тест принудительно отключает все запросы к прежнему маршруту: приложение и редактор восстанавливаются через зеркало, в том числе без DecompressionStream. Все передачи разделяют лимит двух запросов; при сбое старые запросы отменяются. Если зеркало не работает, проверен возврат к исходному источнику. Успех зеркала включает прямой маршрут в тот же Supabase для запросов аккаунта и медиа. JWT, метод и тело сохраняются; потенциально применённая запись не повторяется автоматически через другой путь, платёжные запросы не переносятся. Формат хранения сессии не менялся.

Все 15 наборов тестов прошли. Начальная главная — 15 959 байт gzip; сборка публичных модулей `072f8f89642ddbcb`. Остальные ограничения по проверке на устройстве, письмам после оплаты и чекам сохраняются.

## Повторный сбой загрузки с ноутбука

На присланном снимке окно входа открылось, но загрузчик показал «Не удалось завершить загрузку». Это подтверждает ошибку загрузки приложения, а не неверный пароль. В доступном 45-минутном окне серверного журнала отчёта этого устройства не оказалось. Последующие контрольные POST с нашего клиента дали 201 для диагностики и 200 для первой части SDK, поэтому отсутствие отчёта не объяснено неисправностью этих обработчиков. Точный сетевой или браузерный механизм сбоя на ноутбуке не установлен.

Форма входа теперь не ждёт SDK, редактор, стили редактора и медиа: небольшой встроенный контроллер вызывает существующий Supabase Auth, сохраняет только сессию в совместимом формате и передаёт её основному приложению. Восстановление и регистрация тоже доступны независимо. В тесте отказ всех запросов SDK с HTTP 503 оставляет этот вход рабочим. Проектный SDK реально прочитал полученную тестовую сессию без повторного запроса входа; ответы Auth в этой проверке имитировались, настоящий пароль пользователя не вводился. Проверены отказ хранения, неправильный пароль, таймаут, прямой резервный маршрут к тому же Supabase, повреждённый JSON, повторное нажатие, подтверждение email и запрос восстановления.

Резервная загрузка теперь использует 4096 байт сжатых данных на часть: 22 запроса для всех модулей главной вместо 205. Полные ответы остаются меньше 6 КиБ. Старый формат 384 байта сохранён для закэшированных страниц. Восстановление всех настоящих модулей проверено в обоих форматах с SHA-256. Ошибка на странице содержит модуль, причину и HTTP-код; сервер журналирует только разрешённые коды. Начальный HTML после закреплённого Terser — 15 676 байт gzip. Все 14 наборов тестов прошли. Рабочий прокси Auth на пустой запрос без учётных данных вернул ожидаемый HTTP 400 `validation_failed: missing email or phone`; это проверка маршрута, не успешного входа пользователя.

Эти результаты не подтверждают успешный новый вход именно с ноутбука пользователя и не снимают отдельные ограничения по письмам после оплаты и чекам ниже.

Обновление после повторного сообщения с ноутбука: предыдущая проверка в удалённом Chrome не подтвердила работу на устройстве пользователя. В последнем 15-минутном окне отчёт со старой страницы не поступил; точная причина этого не установлена. Найдена зависимость всех кнопок от кода в конце большого документа. Загрузка переделана: ранние обработчики, небольшой начальный HTML, отдельный редактор и резервные ответы меньше 1 КиБ.

Дополнительные проверки: окно входа открывается в тесте незавершённого документа без SDK/приложения; ответы HTTP 200 с зависшим телом принудительно обрываются; все реальные модули побайтно восстанавливаются из маленьких gzip-ответов и режима без DecompressionStream. В браузере принудительный delivery=small открыл окно входа, когда элемента скрипта приложения ещё не было; затем редактор загрузился и пустая форма показала русскую валидацию. Аналогично форма админки доступна до её большого скрипта. На момент записи результат на ноутбуке пользователя ещё не подтверждён.

После этой правки `npm test` содержит 13 наборов. Проверки серверного подтверждения оплаты и SQL сохраняют силу: эти обработчики в данной правке не менялись. Исторические описания поставки с полностью встроенным SDK ниже относятся к предыдущей версии.

Проверен текущий код сайта и серверных обработчиков, исходники трёх Edge Functions, схема восьми таблиц, политики RLS, права, триггеры, индексы и старые скрипты загрузки. Основной исправляющий коммит: `7ea854de11c9a305f753098fb69dd8d82aa7d3e0`. Сторонний минифицированный SDK использован как поставляемая зависимость; независимый аудит каждой его строки не проводился.

## Автоматические тесты

`npm test` запускает каждый набор в отдельном процессе. На исправляющем коммите прошли 10 наборов: загрузка текущих и закэшированных страниц, диагностика, полное тело ответа и отмена запроса, порядок сохранений, медиа, checkout, защита подтверждения оплаты и резервное чтение. Отсутствие строки PASS тоже считается ошибкой, чтобы незавершённый асинхронный тест не считался успехом.

Проверки базы выполнены с настоящими ролями anon/authenticated и с откатом транзакций; данные клиентов и доступ администратора не использовались для тестовых изменений.

## Оставшиеся ограничения

1. Автоматические письма с инструкцией не подключены. Vercel не дал подключённому доступу управлять интеграциями (403). Настроенного почтового сервиса в переменных проекта нет.
2. Получение клиентом чека не подтверждено; фискальные настройки рабочего магазина не доступны в этой проверке. Автоматическая обработка возвратов в приложении отсутствует.
3. На последней сборке не выполнены новый вход с настоящим паролем, получение письма восстановления, новый вход администратора и новая покупка. Эти результаты нельзя приравнивать к проверке пустой формы или тесту серверной функции.
4. Проверка выполнена в удалённом Chrome, а не на ноутбуке пользователя. Для устранения его конкретного сбоя нужно подтвердить запуск новой страницы на устройстве. Автоматический отчёт фиксирует наличие встроенных модулей, не собирает пароль или адрес почты и не доказывает успешный вход.
5. Supabase сообщает об отключённой проверке утёкших паролей. Открытое выполнение ограниченной функции submit_rsvp — намеренное: иначе гости не смогут отвечать без регистрации. Таблицы администраторов и промокодов без клиентских RLS-политик намеренно закрыты. Предупреждение о search_path устранено; недостающие индексы внешних ключей добавлены. Два дублирующихся индекса остались; попытка удаления завершилась ошибкой инструмента `Invalid or expired requestState` и не была применена.

Эта поставка исправляет обнаруженные ошибки и содержит воспроизводимые проверки. Она не является обещанием отсутствия любых будущих ошибок или полной готовности почты и чеков.
